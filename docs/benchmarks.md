# ベンチマーク

nib と既存のエディタ（vim、Neovim、Helix、Emacs）を同じ条件で測った結果。目標は [architecture.md](architecture.md) の「性能目標」にある。

## 測り方

[bench/latency.py](../bench/latency.py) で、疑似端末（pty）越しにエディタを動かして測る。端末エミュレータの遅延は含まない。端末の大きさは 160 × 50。

| 項目 | 内容 |
|------|------|
| 起動 | 起動してから、描画が 0.3 秒止まるまで。最初の画面のあとに色を付けて描き直すエディタは、その描き直しまで含む。モードの設定だけの書き出し（`ESC[?1004h` など）は描画に数えない。10 回の中央値 |
| 打鍵 | 挿入モードでファイルの先頭に `a` を 300 回打ち、キーを送ってから画面の書き出しが終わるまで |
| スクロール | 画面送りを 300 回。40 回ごとに先頭に戻る。vim、Neovim、Helix、nib は半画面（`Ctrl-d`）、Emacs は 1 画面（`C-v`） |
| メモリ | macOS の `proc_pid_rusage` の物理メモリの使用量（アクティビティモニタの「メモリ」と同じ）を、エディタとその子孫のプロセスで合計したもの。起動の直後と、打鍵とスクロールのあと |
| 待機 | キーを待っているあいだの 30 秒の CPU 使用率と、1 秒あたりのウェイクアップ回数（`--idle 30`） |

どのエディタも、ユーザーの設定なしで、LSP を切って動かす（vim と Neovim は `--clean`、Emacs は `-nw -Q`、Helix は LSP を切った設定、nib は `plugins/lsp.toml` に `enabled = false` を書いた一時的な設定）。

ベンチは端末の代わりに、エディタの問い合わせに答える（1 次と 2 次の DA、XTVERSION、背景色と前景色、状態、カーソルの位置）。答えは、問い合わせが届いた順に返す。

### 読むときの注意

- **ハイライトの仕組みがエディタごとに違う**。同じファイルでも、している仕事が違う。

  | ファイル | vim | Neovim | Helix | Emacs | nib |
  |----------|-----|--------|-------|-------|-----|
  | Rust | 正規表現 | 正規表現 | tree-sitter | なし（`fundamental-mode`） | tree-sitter |
  | Markdown | 正規表現 | tree-sitter（コードブロックの中は色なし） | tree-sitter（injection あり） | 正規表現（ファイル名から `change-log-mode`） | tree-sitter（injection あり） |

  Neovim は Markdown の文法を同梱し、tree-sitter で色を付ける。Rust の文法は同梱していないので、Rust のファイルと Markdown の中の Rust のコードブロックは、vim と同じ正規表現で色を付けるか、色を付けない。
- **打鍵とスクロールは「画面の書き出しが終わるまで」**。vim と Neovim はスクロールで最初の数バイトをすぐに書き、残りをあとから書くので、最初のバイトまでの時間では速く見える。
- **CPU の省電力で値が大きく変わる**。キーの合間に CPU が省電力の状態に落ち、次のキーを遅いクロックで処理するため。裏で CPU を 1 コア回しておくと、nib の Rust 大の打鍵は 2.06 ms から 0.87 ms になった（解析を裏のスレッドに移す前の値）。実際に打つときもキーの合間は空くので、何もしていないマシンでの値を載せる。
- **同じマシンでも、測った時によって 3 割ほどずれる**。比べるときは、同じ時に測った値どうしで比べる。p99 は、同じ設定でも測るたびに 2〜8 ms 動く。
- **打つ場所で解析の重さが変わる**。ファイルの先頭の `use std::io;` の前に `a` を打つと構文エラーになり、tree-sitter のエラー回復が走る。nib の構文木の更新（プロセスの中、CPU が温まった状態）は、打つ場所によって次のように変わる。今の nib は解析を裏のスレッドで行うので、打鍵の遅延には表れない。

  | 打つ場所（Rust 大） | 構文木の更新（中央値） |
  |---------------------|------------------------|
  | ファイルの先頭の `use` の前（構文エラーになる。ベンチの条件） | 1.26 ms |
  | ファイルの途中の識別子の中 | 0.12 ms |
  | ドキュメントコメントの中 | 0.05 ms |
  | ファイルの終わり | 0.12 ms |

- vim と Neovim は強制終了するとスワップファイルを残し、次の起動が問いの画面で止まる。ベンチは `-n`（スワップファイルなし）で起動する。
- 実行ファイルを起動するだけのラッパーが `exec` せずに本体を起動すると、ラッパーの分もメモリと起動の時間に入る（mise で入れた Emacs は、`sh` のラッパーで 1.6 MB と 6 ms 多く出た）。ベンチには本体を渡す（`BENCH_EMACS` など）。

### ファイル

中身が変わらないように、crates.io のクレートに入っているファイルを使う（`~/.cargo/registry/src/*/` にある）。

| 名前 | ファイル | 行数 | 特徴 |
|------|----------|------|------|
| Rust 大 | ropey 1.6.1 `src/rope.rs` | 3,455 | ドキュメントコメント 592 行 |
| Rust 小 | 上の先頭 20 行（`head -n 20`） | 20 | ドキュメントコメントを 1 行含む |
| テキスト | 「Rust 大」を `rope.txt` に写したもの | 3,455 | 構文ハイライトなし。ハイライトの費用を見るため |
| Markdown | ratatui 0.29.0 `CHANGELOG.md` | 6,969 | コードブロック約 360、行内のコード約 1,000 |

### 再現

Neovim と Emacs は mise で入れた（Emacs は conda の backend。`MISE_EXPERIMENTAL=1` が要る）。

```sh
mise install neovim@0.12.5
MISE_EXPERIMENTAL=1 mise install conda:emacs@31.1
export BENCH_NVIM=$(mise where neovim@0.12.5)/bin/nvim
export BENCH_EMACS=$(MISE_EXPERIMENTAL=1 mise where conda:emacs@31.1)/Emacs.app/Contents/MacOS/Emacs
cargo xtask build-plugins
cargo build --release
R=$(echo ~/.cargo/registry/src/*/)
python3 bench/latency.py $R/ropey-1.6.1/src/rope.rs --idle 30 vim nvim hx emacs nib
python3 bench/latency.py $R/ratatui-0.29.0/CHANGELOG.md vim nvim hx emacs nib
NIB_STARTUP_FILE=$R/ropey-1.6.1/src/rope.rs cargo test --release -p nib-core --test syntax startup_breakdown -- --ignored --nocapture
cargo test --release -p nib-core --test plugins key_latency -- --ignored --nocapture
```

### 読み取れること

- tree-sitter でハイライトするエディタ（Neovim の Markdown、Helix、nib）の中では、nib の打鍵がいちばん速く、Markdown で Neovim の 6 分の 1、Helix の 80 分の 1。解析を裏のスレッドで行い、前のフレームの色を使い回して編集した行だけ塗り直すため、ハイライトのないテキストとほぼ同じ時間で済む。
- 正規表現でハイライトするエディタでは、vim は Markdown で速く、Rust で遅い（打鍵 7.6 ms）。Neovim は同じ正規表現の仕組みで Rust を 1.9 ms で処理する。
- Emacs（`-Q`）は Rust に色を付けないが、それでも打鍵は 2〜3 ms かかる。
- 起動は vim と Neovim が速い。nib は、ハイライトなしならいちばん速く、Rust と Markdown で遅いのは構文木を作る分（下の「起動の内訳」）。Neovim の Markdown の起動（121 ms）も、tree-sitter の分。
- メモリは vim が小さく、Neovim がその 2 倍。nib は、テキストでは Neovim と同じくらい、Rust では Emacs や Helix と同じくらい、Markdown では Helix より小さく Emacs より大きい。WASM の実行環境（wasmtime）、プラグインのコンパイル済みコードと線形メモリ、文法の WASM のインスタンス、構文木の分。
- 待機中は、LSP を切れば nib と Helix は CPU もウェイクアップも 0。LSP を使うときは、言語サーバーからのメッセージを受けるたびに起きる。

### injection の費用

同じ時に、injection を外した nib（言語プラグインの `injections` を消したもの）と比べた。

| ファイル | 項目 | injection なし | あり |
|----------|------|----------------|------|
| Rust 大 | 起動 | 34 ms | 52 ms |
| Rust 大 | メモリ（起動の直後） | 17.7 MB | 23.3 MB |
| Rust 大 | 打鍵（中央値 / p99） | 0.63 / 3.93 ms | 0.64 / 3.68 ms |
| Rust 大 | スクロール（中央値 / p99） | 1.09 / 4.06 ms | 1.25 / 3.84 ms |
| Markdown | 起動 | 85 ms | 120 ms |
| Markdown | メモリ（起動の直後） | 25.1 MB | 35.9 MB |
| Markdown | 打鍵（中央値 / p99） | 0.61 / 5.58 ms | 0.73 / 3.10 ms |
| Markdown | スクロール（中央値 / p99） | 1.36 / 3.67 ms | 1.66 / 3.79 ms |

打鍵にはほとんど表れない。起動とメモリの差は、Markdown の文法 2 つの読み込み（文法ごとに WASM のインスタンスを持つ）と、画面の中の層の最初の解析。Rust の色は injection を待たずに先に付く。

## nib の内訳

### 起動の内訳

`startup_breakdown`（プロセスの中で測る。ファイルは Rust 大）。

| 段階 | キャッシュなし | あり |
|------|----------------|------|
| helix プラグインの読み込み | 69.9 ms | 2.8 ms |
| rust と markdown の登録（文法はまだ読まない） | 6.1 ms | 0.5 ms |
| ファイルを開く | 0.4 ms | 0.08 ms |
| 最初の画面（色なし） | 0.08 ms | 0.05 ms |
| Rust の文法の読み込み、解析、色つきの描画 | 34.5 ms | 19.7 ms |
| Markdown の文法の読み込み、画面の中のドキュメントコメントの解析、描画 | 151.8 ms | 14.9 ms |
| 上下 1 画面分の先読み | 0.2 ms | 0.2 ms |
| 合計 | 264 ms | 38 ms |

キャッシュは WASM のコンパイル結果。初回の起動だけがキャッシュなしになる。キャッシュありの Rust の段の中身は、文法の読み込み 5 ms、全体の解析 12 ms、ハイライトのクエリのコンパイル 13 ms（解析と並べて別のスレッドで行う。tree-sitter はコンパイルしたクエリを保存できない）。

実際の起動では、このほかに、プロセスの起動に約 4 ms、標準プラグイン（helix、picker、indent。LSP を切ったとき）のコンパイル結果の読み込みに約 4 ms かかる（メインスレッドともう 1 本で分けて読む。順に読むと 6 ms）。

### プラグインを通る 1 打鍵

条件は Rust 大（3,455 行、ハイライトあり）。

| 指標 | 目標 | 今 |
|------|------|-----|
| 挿入モードの打鍵 | 中央値 2 ms 未満、p99 8 ms 未満 | 0.84 / 5.26 ms |
| スクロール | 中央値 2 ms 未満、p99 8 ms 未満 | 1.58 / 4.92 ms |

## 改善の記録

### 2026-09-27

条件を揃えた（LSP を切った）あとで、次の順に直した。値は同じ日に測ったもの。

| 変更 | 効いたところ |
|------|--------------|
| 埋め込みの文法を写さずに参照する | 起動直後のメモリ（テキスト）15.2 → 9.7 MB |
| 文法のクエリを、最初の解析と並べて別のスレッドでコンパイルする | 起動（Rust 大）87 → 72 ms |
| 起動時のプラグインのコンパイル結果を、スレッドで並べて読む | 起動（テキスト）31 → 27 ms。メモリは 1.8 MB 増えた（スレッドの malloc が抱える分） |
| ASCII の書記素の区切りを Unicode の表を使わずに行う | 画面の組み立て 340 → 160 µs |
| 前の画面との比較を 1 回、行ごとにする | 打鍵（テキスト）0.58 → 0.51 ms |

合わせて、打鍵（中央値）は、テキスト 1.01 → 0.51 ms、Rust 大 2.71 → 1.93 ms、Markdown 2.93 → 2.09 ms になった。

続けて、構文木の解析を専用のスレッドに移した（[architecture.md](architecture.md) の「解析のスレッド」）。打鍵ではテキストの変更を構文木に伝えるだけにして、位置をずらした古い構文木で描き、解析はスレッドで行う。同じ時に比べた打鍵（中央値 / p99）:

| ファイル | 裏で解析しない | 裏で解析する |
|----------|----------------|--------------|
| Rust 大 | 2.41 / 5.15 ms | 1.61 / 3.38 ms |
| Markdown | 2.53 / 6.10 ms | 1.74 / 4.39 ms |

この比較をした時間帯はマシン全体が遅めで、上の表と同じ時ではない。

さらに、前のフレームのハイライトを使い回して編集した行だけを塗り直すようにし、injection の層の解析もスレッドに移した。打鍵（中央値 / p99）は、Rust 大 0.61 / 3.89 ms、Markdown 0.71 / 3.99 ms で、テキスト（約 0.6 ms）とほぼ同じになった。

### 2026-09-28

| 変更 | 効いたところ |
|------|--------------|
| 起動時のプラグインのコンパイル結果を、メインスレッドで順に読む（前日の並べ読みを戻した） | 起動直後のメモリ（テキスト）10.9 → 9.5 MB。プラグインの読み込みは 3.9 → 6.2 ms |
| 性能の優先の順番を決めた（[architecture.md](architecture.md) の「目標」）うえで、メインスレッドともう 1 本で分けて読む形にした | 起動（テキスト）16.8 → 14.1 ms、メモリ 10.0 → 10.7 MB。Rust 大ではメモリの差は測るたびのずれに埋もれた |

並べ読みのスレッドを 4 本から 2 本に絞っても、メモリは減らなかった（1 本増やすだけで 1.4 MB 増える）。長く生きるコンパイル済みコードが、そのスレッドのメモリ領域に散らばって残るためと見ている。`malloc_zone_pressure_relief` で OS に返させても変わらなかった。picker を使うまで起動しない（lazy）ようにしても、メモリは 0.1 MB 前後しか変わらず、見送った。

あわせて、ベンチの応答の仕方を直した。表の順に答えていたため、問い合わせの最後に 1 次 DA を送るエディタ（Neovim、vim）はほかの答えがなかったと見なして待ち、Emacs は 2 次 DA と XTVERSION の答えを約 200 ms 待っていた。前日までの vim の起動の値は、この分だけ遅く出ていた（Rust 小で 40 → 26 ms）。
