# ベンチマーク

nib と既存のエディタ（vim、Helix）を同じ条件で測った結果。目標は [architecture.md](architecture.md) の「性能目標」にある。Neovim と Emacs は、あとで足す。

## 測り方

[bench/latency.py](../bench/latency.py) で、疑似端末（pty）越しにエディタを動かして測る。端末エミュレータの遅延は含まない。端末の大きさは 160 × 50。

| 項目 | 内容 |
|------|------|
| 起動 | 起動してから、出力が 0.3 秒止まるまで。最初の画面のあとに色を付けて描き直すエディタは、その描き直しまで含む。10 回の中央値 |
| 打鍵 | 挿入モードでファイルの先頭に `a` を 300 回打ち、キーを送ってから画面の書き出しが終わるまで |
| スクロール | 半画面スクロール（vim、Helix、nib は `Ctrl-d`）を 300 回。40 回ごとに先頭に戻る |
| メモリ | macOS の `proc_pid_rusage` の物理メモリの使用量（アクティビティモニタの「メモリ」と同じ）。起動の直後と、打鍵とスクロールのあと |
| 待機 | キーを待っているあいだの 30 秒の CPU 使用率と、1 秒あたりのウェイクアップ回数（`--idle 30`） |

どのエディタも、ユーザーの設定なしで、LSP を切って動かす（vim は `--clean`、Helix は LSP を切った設定、nib は `plugins/lsp.toml` に `enabled = false` を書いた一時的な設定）。

### 読むときの注意

- **打鍵とスクロールは「画面の書き出しが終わるまで」**。vim はスクロールで最初の数バイトをすぐに書き、残りをあとから書くので、最初のバイトまでの時間では速く見える。
- **CPU の省電力で値が大きく変わる**。キーの合間に CPU が省電力の状態に落ち、次のキーを遅いクロックで処理するため。裏で CPU を 1 コア回しておくと、nib の Rust 大の打鍵は 2.06 ms から 0.87 ms になった。以前は nib だけ LSP を切っておらず、rust-analyzer が裏で動いて CPU を起こしていたため、nib が実際より速く出ていた。実際に打つときもキーの合間は空くので、何もしていないマシンでの値を載せる。
- **同じマシンでも、測った時によって 3 割ほどずれる**。比べるときは、同じ時に測った値どうしで比べる。
- **打つ場所で重さが変わる**。ファイルの先頭の `use std::io;` の前に `a` を打つと構文エラーになり、tree-sitter のエラー回復が走る。nib の構文木の更新（プロセスの中、CPU が温まった状態）は、打つ場所によって次のように変わる。

  | 打つ場所（Rust 大） | 構文木の更新（中央値） |
  |---------------------|------------------------|
  | ファイルの先頭の `use` の前（構文エラーになる。ベンチの条件） | 1.26 ms |
  | ファイルの途中の識別子の中 | 0.12 ms |
  | ドキュメントコメントの中 | 0.05 ms |
  | ファイルの終わり | 0.12 ms |

- vim は強制終了するとスワップファイルを残し、次の起動が問いの画面で止まる。ベンチは `-n`（スワップファイルなし）で起動する。

### ファイル

中身が変わらないように、crates.io のクレートに入っているファイルを使う（`~/.cargo/registry/src/*/` にある）。

| 名前 | ファイル | 行数 | 特徴 |
|------|----------|------|------|
| Rust 大 | ropey 1.6.1 `src/rope.rs` | 3,455 | ドキュメントコメント 592 行 |
| Rust 小 | 上の先頭 20 行（`head -n 20`） | 20 | ドキュメントコメントを 1 行含む |
| テキスト | 「Rust 大」を `rope.txt` に写したもの | 3,455 | 構文ハイライトなし。ハイライトの費用を見るため |
| Markdown | ratatui 0.29.0 `CHANGELOG.md` | 6,969 | コードブロック約 360、行内のコード約 1,000 |

### 再現

```sh
cargo xtask build-plugins
cargo build --release
R=$(echo ~/.cargo/registry/src/*/)
python3 bench/latency.py $R/ropey-1.6.1/src/rope.rs --idle 30 vim hx nib
python3 bench/latency.py $R/ratatui-0.29.0/CHANGELOG.md vim hx nib
NIB_STARTUP_FILE=$R/ropey-1.6.1/src/rope.rs cargo test --release -p nib-core --test syntax startup_breakdown -- --ignored --nocapture
cargo test --release -p nib-core --test plugins key_latency -- --ignored --nocapture
```

## 結果

2026-09-27、Apple M1 Pro、macOS 27.0、ほかに何も動かしていない状態。vim 9.1、Helix 25.07.1、nib 0.8.12（標準プラグインだけ）。

### Rust 大（3,455 行）

| 項目 | vim | Helix | nib |
|------|-----|-------|-----|
| 起動 | **52 ms** | 168 ms | 68 ms |
| 打鍵（中央値 / p99） | 6.41 / 15.29 ms | 15.68 / 19.14 ms | **1.93 / 6.08 ms** |
| スクロール（中央値 / p99） | 3.03 / 6.36 ms | 2.36 / 6.11 ms | **1.33 / 5.75 ms** |
| メモリ（起動 / 操作のあと） | **5.8 / 5.8 MB** | 23.3 / 21.2 MB | 22.5 / 19.2 MB |
| 待機中の CPU | 0.001 %、0.1 回/秒 | 0.000 %、0.0 回/秒 | 0.000 %、0.0 回/秒 |

### Rust 小（20 行）

| 項目 | vim | Helix | nib |
|------|-----|-------|-----|
| 起動 | **40 ms** | 85 ms | 59 ms |
| 打鍵（中央値 / p99） | 6.85 / 15.64 ms | 1.77 / 5.08 ms | **1.12 / 5.18 ms** |
| メモリ（起動 / 操作のあと） | **5.6 / 5.8 MB** | 15.4 / 15.7 MB | 18.0 / 13.7 MB |

スクロールは、画面に収まるファイルでは何も動かないので測らない。nib の起動は、20 行の中のドキュメントコメントのために Markdown の文法を読み込む分を含む。

### テキスト（3,455 行、ハイライトなし）

| 項目 | vim | Helix | nib |
|------|-----|-------|-----|
| 起動 | 40 ms | 33 ms | **27 ms** |
| 打鍵（中央値 / p99） | **0.17 / 0.46 ms** | 1.05 / 5.28 ms | 0.51 / 3.44 ms |
| スクロール（中央値 / p99） | **0.42 / 0.81 ms** | 1.50 / 4.57 ms | 0.78 / 3.26 ms |
| メモリ（起動 / 操作のあと） | **5.6 / 5.6 MB** | 12.8 / 13.2 MB | 11.4 / 10.9 MB |

### Markdown（6,969 行）

| 項目 | vim | Helix | nib |
|------|-----|-------|-----|
| 起動 | **44 ms** | 401 ms | 139 ms |
| 打鍵（中央値 / p99） | **0.26 / 1.36 ms** | 80.59 / 93.17 ms | 2.09 / 6.07 ms |
| スクロール（中央値 / p99） | 1.52 / 5.73 ms | 2.87 / 6.58 ms | **1.50 / 4.26 ms** |
| メモリ（起動 / 操作のあと） | **6.7 / 6.6 MB** | 50.8 / 51.8 MB | 33.6 / 36.1 MB |

vim の Markdown のハイライトは正規表現で、コードブロックの中を別の言語で色付けしない。Helix と nib は、コードブロックと行内の要素を別の構文木で読む（injection）。

### 読み取れること

- ハイライトのあるファイルでは、nib の打鍵がいちばん速い。vim と Helix は、ハイライトなしなら 1 ms 程度以下だが、Rust のハイライトがあると数 ms から十数 ms になる。構文木を差分で更新し、ハイライトのクエリを表示範囲にだけ掛けているのが効いている。
- nib の打鍵の残りの大半は、tree-sitter の構文木の更新。ベンチの打つ場所（ファイルの先頭）はエラー回復が走るいちばん重い場所で、普通の場所ならその 10 分の 1 で済む（「読むときの注意」）。
- Helix は、injection の多い Markdown で打鍵が 80 ms になる（原因は調べていない）。nib は、画面の近くの層だけを解析して持つことで 2 ms に抑えている（[architecture.md](architecture.md) の「構文木」）。
- 起動は、ハイライトなしなら nib がいちばん速い。Rust で vim より遅いのは、構文木を作る分（下の「起動の内訳」）。vim は見えている行だけに正規表現で色を付ける。
- メモリは vim の 2〜5 倍。WASM の実行環境（wasmtime）、プラグインごとのコンパイル済みコードと線形メモリ、文法の WASM のインスタンス、構文木の分。
- 待機中は、LSP を切れば CPU もウェイクアップも 0。LSP を使うときは、言語サーバーからのメッセージを受けるたびに起きる。

### injection の費用

同じ時に、injection を外した nib（言語プラグインの `injections` を消したもの）と比べた。

| ファイル | 項目 | injection なし | あり |
|----------|------|----------------|------|
| Rust 大 | 起動 | 47 ms | 68 ms |
| Rust 大 | 打鍵（中央値 / p99） | 1.55 / 5.03 ms | 1.93 / 6.08 ms |
| Rust 大 | スクロール（中央値 / p99） | 1.14 / 4.78 ms | 1.33 / 5.75 ms |
| Markdown | 起動 | 102 ms | 139 ms |
| Markdown | 打鍵（中央値 / p99） | 1.30 / 4.40 ms | 2.09 / 6.07 ms |
| Markdown | スクロール（中央値 / p99） | 0.96 / 3.55 ms | 1.50 / 4.26 ms |

起動の差は、Markdown の文法 2 つの読み込みと、画面の中の層の最初の解析。Rust の色は injection を待たずに先に付く。

## nib の内訳

### 起動の内訳

`startup_breakdown`（プロセスの中で測る。ファイルは Rust 大）。

| 段階 | キャッシュなし | あり |
|------|----------------|------|
| helix プラグインの読み込み | 69.3 ms | 3.0 ms |
| rust と markdown の登録（文法はまだ読まない） | 4.9 ms | 0.5 ms |
| ファイルを開く | 0.5 ms | 0.08 ms |
| 最初の画面（色なし） | 0.07 ms | 0.04 ms |
| Rust の文法の読み込み、解析、色つきの描画 | 35.1 ms | 19.9 ms |
| Markdown の文法の読み込み、画面の中のドキュメントコメントの解析、描画 | 158.5 ms | 15.4 ms |
| 上下 1 画面分の先読み | 0.2 ms | 0.2 ms |
| 合計 | 269 ms | 39 ms |

キャッシュは WASM のコンパイル結果。初回の起動だけがキャッシュなしになる。キャッシュありの Rust の段の中身は、文法の読み込み 5 ms、全体の解析 12 ms、ハイライトのクエリのコンパイル 13 ms（解析と並べて別のスレッドで行う。tree-sitter はコンパイルしたクエリを保存できない）。

実際の起動では、このほかに、プロセスの起動に約 4 ms、標準プラグイン（helix、lsp、picker、indent）のコンパイル結果の読み込みに合わせて約 4 ms（スレッドで並べる。順に読むと 10 ms）かかる。

### 1 打鍵の中身

テキストファイルに 1 文字を挿入したとき（pty 越し、CPU は省電力の状態から）。

| 段階 | 時間 |
|------|------|
| 入力のスレッドからメインループへ | 20 µs |
| キーの処理（helix プラグインの呼び出しを含む） | 170 µs |
| 画面の組み立て | 160 µs |
| 前の画面との差分と書き出し | 約 300 µs（大半は端末への `write`） |

CPU が温まった状態でプロセスの中で測ると、キーの処理と画面の組み立てで合わせて 84 µs。`key_latency`（テスト用のプラグインでキーを受けて文字を挿入する 1 回）は 3.2 µs。

### 大きさ

| もの | 大きさ |
|------|--------|
| `nib` の実行ファイル（release、標準プラグインと文法を埋め込み） | 36.6 MB |
| Helix（`hx` と、別に置く文法 `runtime/grammars`） | 15.5 MB + 190 MB |
| vim | 8.1 MB |

埋め込んでいる標準プラグイン（WASM の合計）:

| プラグイン | 大きさ | プラグイン | 大きさ |
|------------|--------|------------|--------|
| bash | 1,326 KB | markdown（ブロックと行内） | 828 KB |
| rust | 1,092 KB | lsp | 370 KB |
| python | 447 KB | helix | 327 KB |
| go | 212 KB | indent | 188 KB |
| yaml | 185 KB | picker | 108 KB |
| toml | 23 KB | json | 5 KB |

## 目標との比較

条件は Rust 大（3,455 行、ハイライトあり）。

| 指標 | 目標 | 今 |
|------|------|-----|
| 挿入モードの打鍵 | 中央値 2 ms 未満、p99 8 ms 未満 | 1.93 / 6.08 ms |
| スクロール | 中央値 2 ms 未満、p99 8 ms 未満 | 1.33 / 5.75 ms |
| 起動から最初の描画まで（キャッシュあり） | 100 ms 未満 | 68 ms（色付けまで） |
| 1 つのプラグインが 1 回のイベントに使う時間 | 1 ms 未満を目安 | 3.2 µs（test-insert） |

打鍵は、構文エラーになる場所（ベンチの条件）で目標のぎりぎりにある。Markdown（6,969 行）では中央値 2.09 ms と、少し超える。

## 改善の記録

### 2026-09-27

条件を揃えた（LSP を切った）あとで、次の順に直した。値は同じ日に測ったもの。

| 変更 | 効いたところ |
|------|--------------|
| 埋め込みの文法を写さずに参照する | 起動直後のメモリ（テキスト）15.2 → 9.7 MB |
| 文法のクエリを、最初の解析と並べて別のスレッドでコンパイルする | 起動（Rust 大）87 → 72 ms |
| 起動時のプラグインのコンパイル結果を、スレッドで並べて読む | 起動（テキスト）31 → 27 ms。メモリは 1.8 MB 増えた（スレッドの malloc が抱える分） |
| ASCII の書記素の区切りを Unicode の表を使わずに行う | 画面の組み立て 340 → 160 µs |
| 前の画面との比較を 1 回、行ごとにする | 打鍵（テキスト）0.58 → 0.51 ms |

合わせて、打鍵（中央値）は、テキスト 1.01 → 0.51 ms、Rust 大 2.71 → 1.93 ms、Markdown 2.93 → 2.09 ms になった。

続けて、構文木の解析を専用のスレッドに移した（[architecture.md](architecture.md) の「解析のスレッド」）。打鍵ではテキストの変更を構文木に伝えるだけにして、位置をずらした古い構文木で描き、解析はスレッドで行う。同じ時に比べた打鍵（中央値 / p99）:

| ファイル | 裏で解析しない | 裏で解析する |
|----------|----------------|--------------|
| Rust 大 | 2.41 / 5.15 ms | 1.61 / 3.38 ms |
| Markdown | 2.53 / 6.10 ms | 1.74 / 4.39 ms |

この比較をした時間帯はマシン全体が遅めで、上の表と同じ時ではない。

さらに、前のフレームのハイライトを使い回して編集した行だけを塗り直すようにし、injection の層の解析もスレッドに移した。打鍵（中央値 / p99）は、Rust 大 0.61 / 3.89 ms、Markdown 0.71 / 3.99 ms で、テキスト（約 0.6 ms）とほぼ同じになった。

## これまでの推移

各マイルストーンを終えたときに記録した値（[roadmap.md](roadmap.md)）。条件は Rust 大で、そのときの機能での値。測った時と条件（LSP の有無、CPU の状態）が違うので、上のずれの幅を見込んで読む。

| 時点 | 起動 | 打鍵（中央値 / p99） | スクロール（中央値 / p99） | そのときの状態 |
|------|------|----------------------|----------------------------|----------------|
| M0.2 | 10 ms | | | 表示だけ。プラグインもハイライトもない |
| M0.3 | 15.5 ms | 0.97 / 1.68 ms | | テスト用のプラグインで文字を挿入 |
| M0.4 | 9.9 ms | 0.73 / 2.44 ms | | helix プラグインを埋め込み |
| M1 | 13.1 ms | 0.87 / 3.90 ms | 1.14 / 5.72 ms | 待機中の CPU は 0.008 % |
| M2.1 | 58.9 ms | 1.81 / 6.67 ms | 1.30 / 4.82 ms | 構文ハイライト |
| M2.3 | | 2.41 / 5.26 ms | | 対応する括弧の強調 |
| M3.2 | | 1.29 / 6.16 ms | | 入力の読み取りを別のスレッドに |
| M2.5 | 68 ms | 1.93 / 6.08 ms | 1.33 / 5.75 ms | injection と、この日の改善（この文書の結果） |

M2.2 では、構文木を使う操作を別に測った: `]f` が 3.6 ms、`Alt-o` が 2.6 ms。
