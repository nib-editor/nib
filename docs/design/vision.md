# ビジョン

> ステータス: 合意済み（2026-09-25）

## nib とは

すべての機能を WebAssembly プラグインで組み立てるモーダルエディタ。コアは最小限にとどめ、キーマップや編集コマンドといった「エディタらしさ」の大半をプラグインとして実装する。

## なぜ作るか

vim と emacs は拡張性でエディタの歴史をつくってきたが、今から見ると次の制約がある。

- **拡張言語が固定されている。** vim は Vimscript / Lua、emacs は Emacs Lisp。拡張を書くには、まずその言語を覚える必要がある。
- **拡張が本体と同じ権限で動く。** プラグインはファイルシステムやネットワークに無制限にアクセスできる。どのプラグインが何をしているか、ユーザーからは見えない。
- **編集モデルが本体に組み込まれている。** vim の「動作 → 対象」や Helix の「選択 → 動作」といった編集の文法は本体の設計そのもので、差し替えは想定されていない。emacs は evil のように差し替えられるが、その自由度は、拡張が Elisp で本体と同じ権限で動くことと引き換えになっている。

nib はこれを WebAssembly Component Model で解決する。

- プラグインは WIT で定義された API に対して書く。Component Model に対応した言語なら何でもよい。
- プラグインはサンドボックス内で動き、ファイル・プロセス・ネットワークのどれを使うかが外から見える。
- 編集モデル（モード、キーマップ、選択の操作）もプラグインが提供する。

### 先行例との違い

Zed も拡張に WebAssembly を使っているが、拡張の対象は主に言語サポートやテーマで、キーマップや編集モデルは本体側にある。nib は編集モデルそのものをプラグインで提供する点が違う。

## 目標

1. **言語を問わずプラグインを書ける。** 公式 SDK はまず Rust と Go を用意する。
2. **コアを小さく保つ。** コアが持つのはバッファ、選択、描画、プラグインホストと、複数のプラグインが共有する基盤だけ。コアに入れるのは次のどちらかに当てはまるものに限る。
   - プラグインからは実現できない
   - 複数のプラグインが共有する基盤で、各プラグインに持たせると重複や性能の問題が出る

   たとえば tree-sitter の解析基盤は後者に当たるのでコアに置き、文法とハイライトの定義はプラグインが提供する。LSP クライアントは非同期で遅延を許容できるのでプラグインにする。
3. **標準機能も公開 API で書く。** 標準プラグインはコアの内部に依存しない。標準プラグインで困ることはサードパーティのプラグインでも困るので、API の不足がすぐに見える。
4. **プラグインが何をするか見えるようにする。** ファイル・プロセス・ネットワークは WIT 上で別々のインターフェースに分け、どのプラグインがどれを使うかを一覧できるようにする。プラグインは使う権限を宣言し、宣言したものは確認なしで与え、宣言していないものは与えない。
5. **普段使いできる速さ。** プラグインを経由しても、キー入力から描画までの遅延を感じさせない。具体的な数値目標は architecture.md で決める。

## 目的外

- **vim / emacs との互換。** キーバインドや設定ファイルの互換は目指さない。vim 風キーマップはプラグインとして作れる状態にするが、本体の目標にはしない。
- **組み込みのスクリプト言語。** Lua や Lisp のような拡張言語をコアに持たない。拡張の手段は WASM プラグインに一本化する。
- **GUI（当面）。** まずターミナルで動かす。ただし「何を表示するか」と「どう描くか」は分けておき、あとから GUI の描画を足せる余地を残す。
- **コードで書く設定。** init.el や init.lua のような設定は持たない。設定は宣言的な TOML ファイル 1 つで、コアの設定（`[core]`）と、プラグインごとの設定を同じ書き方で書く。ロジックが必要なら小さなプラグインを書く。

## 位置づけ

**現代版の Emacs** を目指す。Emacs のように何でも拡張できて、しかも拡張がサンドボックスの中で安全に動き、どの言語でも書けるエディタ。

もう 1 つは、**AI に作らせるエディタの土台**。AI に「こういうエディタがほしい」と伝えて、nib の上にプラグインとして作ってもらう使い方を想定する。これまでの設計は、この使い方と噛み合っている。

- AI が書いたコードは、中身を確かめきれないまま動かしがち。nib ではサンドボックス、権限の宣言、時間とメモリの上限、壊れたときの再起動、コアメニューが、そのまま安全網になる。
- API は型のついた 1 つの定義（WIT）にまとまっていて、AI が読みやすい。書く言語も選ばない。
- プラグインを作り直したら、エディタを再起動せずにコアメニューから読み直せる。

## 想定ユーザー

作者自身。作者が毎日使えるエディタになることを最優先にする。プラグインの配布の仕組み、API の安定性の保証、利用者向けのドキュメントといった他人向けの整備は後回しにする。

ただし、いずれは他の人にも使ってもらうことを見据える。特定の人の環境や好みに依存した選び方（そのキーマップでしか使えない予約キーなど）はしない。

## 最初のマイルストーン

Helix 風キーマップのプラグインだけで、nib 自身のソースコードを編集できること。

これが動けば、「標準機能もプラグイン」という設計が成り立つことを確かめられる。詳細は roadmap.md で決める。
