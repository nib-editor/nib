# プラグインの配布とインストール

> ステータス: 実装済み（2026-09-26、M4.6）。名前で探せる一覧は M4.9 で足した。

標準プラグインのほかに、ほかの人が作ったプラグインを入れられるようにする。`nib plugin search` で探し、`add` で入れ、`update` で更新し、`remove` で外す。

## 方針

- **URL ベースで始める。** プラグインの身元は取得元の URL にする（Go のモジュールや lazy.nvim の `owner/repo` と同じ）。
  - サーバーが要らない。名前の取り合いも起きない。
  - GitHub にリリースを作るだけで公開できる。AI が作ったプラグインも気軽に配れる。
- **配るのはビルド済みのもの。** ソースから組み立てる方式は、利用者に Rust と wasm のツール一式を求めることになるので採らない。
- **名前で探せる一覧は、git リポジトリに置いた TOML 1 つにする**（下の「名前で探す」）。サーバーを持つレジストリ（crates.io や npm のようなもの）は作らない。運用、アカウント、名前の横取り対策、悪意あるプラグインへの対応が、今の規模には重いため。
- **仕事はすべて tui のサブコマンドで行い、コアは変えない。** インストール中に、プラグインのコードは一切動かさない。

## 配布の形

プラグインのディレクトリ（`plugin.toml`、`plugin.wasm`、クエリなどのデータ）を、そのまま `.tar.gz` にまとめる。名前の末尾は `.nib.tar.gz` にする。GitHub のリリースにほかのファイルが並んでいても、見分けられるようにするため。

```
nib-foo-0.1.0.nib.tar.gz
├── plugin.toml
├── plugin.wasm        # データだけのプラグインにはない
└── queries/...
```

プラグインの作者は、`nib plugin pack <dir>` でこの形のアーカイブを作る。`<dir>` はビルド済みのディレクトリ（`nib plugin build` のあとのプラグインのディレクトリや、`cargo xtask build-plugins` が作る `target/plugins/<name>/`）。入れるのは nib が読むものだけ: `plugin.toml`、`plugin.wasm`、`[[languages]]` が指す文法とクエリ、`LICENSE*`。ソースやビルドの途中のファイル（`src/`、`target/`）は入れない。

## 入れ方

```sh
nib plugin add someone/nib-foo                  # GitHub の最新のリリース
nib plugin add github.com/someone/nib-foo       # 同じ
nib plugin add someone/nib-foo@v0.2.0           # そのタグのリリース
nib plugin add https://example.com/foo-0.1.0.nib.tar.gz   # アーカイブの URL を直接
nib plugin add ./foo-0.1.0.nib.tar.gz           # 手元のアーカイブ（作者が自分のビルドを試すとき）
nib plugin add foo                              # 一覧で foo の取得元を引く（下の「名前で探す」）
```

`add` の流れ:

1. 取得元を決める。
   - GitHub の場合は、`https://api.github.com/repos/<owner>/<repo>/releases/latest`（またはタグのリリース）を読み、`.nib.tar.gz` で終わるファイルを探す。1 つでなければエラーにする。
   - 認証はしない。未認証の API は 1 時間に 60 回までだが、インストールと更新には足りる。
2. ダウンロードする。`cargo xtask build-plugins` と同じく、`curl` を外部プロセスとして使う（`https` だけを許す）。Windows 10 以降にも `curl` はある。
3. 一時ディレクトリに展開して、中身を確かめる。
   - 絶対パス、`..` を含むパス、シンボリックリンクは拒む。展開後の合計が 100 MiB を超えたら止める。
   - マニフェストが読めること、`api` のバージョンが nib と合うこと、名前が正しい形であること。
   - 名前が、標準プラグインやインストール済みの別の取得元のプラグインとぶつからないこと。プラグインの名前はコマンドの名前空間（`lsp.hover` の `lsp`）を兼ねるので、同じ名前は並べられない。
4. **確認を取る。** 名前、バージョン、取得元、宣言している権限と購読するイベントを表示し、入れてよいか尋ねる（`--yes` で省ける）。読み込むときは権限を確認なしで与える設計なので（[plugin-api.md](plugin-api.md) の「権限」）、同意を取る場所はインストールの時点しかない。
5. `~/.local/share/nib/installed/<name>/` に置く（`$XDG_DATA_HOME` があればその下、Windows では `%LOCALAPPDATA%\nib\installed\`）。一時ディレクトリから名前を変えて移すので、途中で失敗しても半端なものは残らない。
   - `~/.local/share/nib/plugins/<name>/` は、プラグインが自分の状態を書くデータディレクトリとして取ってあるので、そことは分ける。
6. 記録ファイル `~/.local/share/nib/installed.toml` に、名前、取得元（打った形のまま）、実際に取った URL とタグ、バージョン、sha256、同意した権限を書く。

入れたプラグインは、次に nib を起動したときから読み込まれる。

`--yes` を付けると、確認を省いて入れる（スクリプトから使うとき）。付けずに、端末でない入力から動かしたときは、答えがないので入れない。

## 名前で探す

一覧は git リポジトリ [nib-editor/plugins](https://github.com/nib-editor/plugins) の `plugins.toml` に置く。mise の registry と同じ考え方で、サーバーは持たない。

```toml
[[plugin]]
name = "wordcount"
source = "nib-editor/plugin-example"   # add が受け取る形なら何でもよい
description = "Shows the buffer's word count in the status line (an example in Go)"
```

```sh
nib plugin search            # 一覧のすべて
nib plugin search status     # 名前か説明に status を含むもの（大文字と小文字は区別しない）
nib plugin add wordcount
nib plugin add wordcount@v0.1.0   # そのタグのリリース
```

- 一覧は、使うたびに `https://raw.githubusercontent.com/nib-editor/plugins/main/plugins.toml` から `curl` で取る。手元には保存しない。小さいファイルなので、毎回取っても困らない。
- `add` は、引数に `/`、`\`、`:`、`@` がなく、`.nib.tar.gz` で終わらなければ名前とみなす。一覧でその名前の `source` を引き、あとは取得元を直接渡したときと同じ手順で入れる。
  - 記録ファイルの取得元には、名前ではなく引いた `source` を書く。身元はあくまで取得元で、一覧は近道でしかない。`update` も一覧を見ずに、記録した取得元から取る。
  - 名前のあとに `@タグ` を付けると、一覧の `source` にそのタグを付けて入れる（`wordcount@v0.1.0` → `nib-editor/plugin-example@v0.1.0`）。記録にもタグつきの取得元が残るので、`update` の対象にならない。タグを選べるのは `source` が GitHub のリポジトリで、一覧がタグを決めていないときだけ。
  - 取ったプラグインのマニフェストの名前が一覧の名前と違えば、入れない。一覧が指す先を取り違えていても、別の名前のものが入らないようにするため。
- 一覧への登録は PR で受ける。一覧のリポジトリの CI は、項目がそろっていること、名前が正しい形で重ならず名前順であることだけを確かめる。一覧に載っていても中身を保証するものではなく、守りはインストール時の権限の確認に任せる。
- サンプルとして、Go で書いたプラグイン [nib-editor/plugin-example](https://github.com/nib-editor/plugin-example)（`wordcount`）を載せてある。タグを push するとリリースの `.nib.tar.gz` を作るワークフローも持つので、プラグインを公開するときのひな形になる。

## 読み込み

- nib は、インストール済みのプラグインを記録ファイルから読み、標準プラグインのあとに読み込む。`plugins/<name>.toml` を書かなくても動く。
- `plugins/<name>.toml` は、これまでどおり設定だけを書く場所（`enabled`、上限、`load`、`[settings]`）。
  - `path` を書けば、インストールしたものの代わりにそちらを読む（標準プラグインを `path` で置き換えるのと同じ）。
- `nib plugin list` は、インストール済みのものの SOURCE に取得元の URL を出す。
- 読み込めないプラグイン（nib を更新して API が合わなくなったものなど）は飛ばして起動し、理由をメッセージで出す。nib 自体が起動しなくなることはない。`--plugin` で手で渡したものだけは、読み込めなければエラーで止める。

## 更新と削除

```sh
nib plugin update           # すべて
nib plugin update foo       # foo だけ
nib plugin remove foo
```

- `update` は、記録した取得元から最新のリリースを取り直す。
  - タグを指定して入れたもの（`@v0.2.0`）と、アーカイブの URL や手元のアーカイブで入れたものは更新しない。
  - アーカイブの sha256 が前と同じなら何もしない。
  - 新しい版の権限が、前に同意した権限より増えていたら、差分を表示して確認を取り直す。増えていなければ確認なしで入れ替える。
- Ctrl-g のコアメニュー（[core-menu.md](../core/core-menu.md)）からも更新できる。プラグインを選ぶと、リリースを追っているもの（GitHub から、タグを指定せずに入れたもの）には `Update` が出る。
  - 確かめて取るのは裏のスレッドで行い、そのあいだもエディタは動く（「待たせない」）。終わると、メッセージで結果を知らせる（最新だった、失敗した理由）。
  - 新しい版が前より多くの権限を求めるときは、メニューに増える権限を出して確認する（`[y] update`、ほかのキーでやめる）。`nib plugin update` と同じ決まり。
  - 入れ替えたら、その場でディスクから読み直す。再起動は要らない。
  - 取ってくるのも入れ替えるのもフロントエンドの仕事（コアはネットもファイルの置き場も知らない）。コアは、フロントエンドが渡す口（`PluginStore`）を呼ぶだけ。渡されなければ `[u]` は出ない。
- コアメニューからは、入れることと消すこともできる。
  - 最初の一覧の `Add a plugin` で、`add` が受け取る形（名前、`名前@タグ`、`owner/repo[@tag]`、URL）を打ち込む。`Enter` で、裏のスレッドで取ってきて確かめ、名前、版、求める権限を見せて聞く（`y` で入れる）。入れたら、その場で読み込む。
  - 入れたプラグインのページの `[x] remove` で、確かめてから止めて、ファイルと記録を消す。設定とデータは残す。エディタの中で読み込んだものは外せないので、次に起動するまで一覧に無効として残る。
- `remove` は、インストールしたファイルと記録を消す。`plugins/<name>.toml`（利用者の設定）とデータディレクトリは消さず、残っていることを表示する。

## 先にそろえること: API のバージョン

配布を始めると、古い SDK で作られたプラグインが混ざる。M4.6 までは WIT のパッケージが `nib:plugin@0.1.0`、マニフェストの `api` も `"0.1"` のままで、破壊的な変更をしても上げていなかった（SDK だけ 0.4 まで上がっていた）。これでは、合わないプラグインを入れる前に見分けられない。

- WIT のパッケージのバージョンを SDK にそろえる（M4.6 で `nib:plugin@0.4.0` にした）。以降は WIT を変えたら、同じコミットで両方を上げる。
- マニフェストの `api` は、その `メジャー.マイナー`（`"0.4"`）にする。nib は、自分と違う `api` のプラグインを入れず、読み込まない。

## 使うクレート

- 展開: `tar` と `flate2`（tui の依存に足す）
- JSON: `serde_json`（GitHub の API の応答を読む。すでに依存にある）
- ダウンロードは `curl` を呼ぶので、HTTP のクレートは足さない

## あとで足すもの

- **別名での導入。** 同じ名前のプラグインを並べたくなったら、入れるときに名前を付け替える方法を考える。コマンドの名前空間が変わるので、実際に困ってから決める。
