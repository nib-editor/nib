# プラグインが中身を持つバッファ

> ステータス: 合意済み（2026-09-28）。nib 0.11.0 と `nib:plugin@0.7.0` で入れた。

magit や dired のように、プラグインがバッファそのものを UI にする仕組み（[roadmap.md](../project/roadmap.md) の「保留中のアイデア」）。プラグインが中身を書き、利用者はふつうのバッファと同じく、ベースのキーで動き、探し、選ぶ。そのうえで、そのバッファでだけ効くキーでプラグインの操作を呼ぶ。

## なぜバッファか

今のプラグインの画面は、パネル（下の行）、ポップアップ（本文の上の箱）、入力欄と一覧（picker、補完）。どれも短い間だけ出るもので、中を動き回れない。診断の一覧、grep の結果、ファイルの一覧、git の状態のように、長く開いておいて行を選んで操作したいものは、バッファにするのがいちばん手間が少ない。

- 動き、検索、選択、スクロール、分割、バッファの切り替えは、ベースとコアのものがそのまま効く。プラグインごとに一覧の操作を作らなくてよい。
- 利用者は、どのベースを使っていても、覚えたキーで一覧を動ける。
- Emacs では、ヘルプ、バッファの一覧、grep、dired、magit がどれもこの形で、エディタの性格の芯になっている。

パネル、ポップアップ、入力欄はそのまま残す。キーの案内、ホバー、補完、picker のように、短い間だけ出て、本文から目を離さずに使うものに向いているため。

## 形

### 作る

- `buffer.create(name)` で、パスのないバッファを作る。`name` は `*diagnostics*` のように、ステータスラインとバッファの一覧に出る名前。作っただけでは表示しない。表示は今ある `view.show`（分割してから表示するなら `view.split` のあと）。
- 作ったプラグイン（持ち主）が止まると、コアが閉じる。持ち主は `buffer.close` でも閉じられる。利用者も、ほかのバッファと同じく閉じられる。`buffer-closed` は、パスのほかに名前も渡すので、持ち主は自分のバッファが閉じたと分かる。
- `buffer.name()` を足す。ふつうのバッファではパス、プラグインのバッファでは付けた名前、どちらもなければ `[scratch]`。

### 書く

- 中身を書くのは持ち主だけで、`buffer.apply`（表示していなくても書ける）を使う。ビューでの編集（`view.apply`、undo、redo）は、持ち主のものも含めて `read-only` の失敗になり、コアが「`*diagnostics*` is read-only」と知らせる。
  - 持ち主も断るのは、ベースが自分のバッファ（vim の `*registers*`、Emacs の `*Help*`）を持つとき、ベースの編集のキーで中身が変わらないようにするため。
- 持ち主が `buffer.set-editable(true)` にすると、ビューで編集できる（Emacs の wdired のように、一覧を書き換えてからまとめて反映する使い方のため）。持ち主は `buffer-changed` で変更を知る。
- 保存はしない（パスがない）。変更済み（`modified`）にもならないので、終了のときに聞かれない。
- 色は、今ある装飾（`ui.set-decorations`）と注記で付ける。行とプラグインの中の項目の対応は、持ち主が持つ（書き直すのも持ち主なので、行の番号で足りる）。

### キー

そのバッファでだけ効くキーを、持ち主が決める。

- `buffer.set-keys(keys)` で、キー（設定と同じ書き方。`ret`、`s`、`C-c C-c`）とコマンド（自分のもの）の組を渡す。コマンドは、今と同じく `commands.register` で登録したもの。呼ばれたコマンドは、`view.active()` の選択で、どの行で押されたかを知る。
- キーを受けるのは、今と同じくベース。ベースは、フォーカスのあるバッファのキーを `buffer.keys()` で読み、自分の作法で組み込む。
- ベースが自分のバッファに自分のコマンド（`vim.close-listing`、`emacs.quit-window`）を付けたときは、コマンドとして呼ばずに自分で動かす。コアは呼び出し中のプラグインを呼び返せないため。コマンドラインや `M-x` で名前を打たれたときも同じ（base-kit の `own_command`）。
  - API で解くなら、結果を待たずに今の呼び出しのあとで動かす `commands.post` のようなものになる。困るのがベースの自分のバッファだけのうちは足さない。1.x でも関数は足せるので、要るようになってからでよい。
- どのキーを譲るかはベースが決める。

| ベース | 決まり |
|--------|--------|
| Emacs、nano | バッファのキーが先（Emacs のメジャーモードの表と同じ）。文字は打てないので、ふつうの文字のキーも使える |
| vim、helix | normal モードでは、バッファのキーが先。ただし、ベースが手放さないキー（動き、検索、`:`、ウィンドウ、リーダー、Esc）はベースのまま |

- 手放さないキーは、各ベースの文書に書く（vim なら `h` `j` `k` `l` `w` `b` `e` `gg` `G` `/` `?` `n` `N` `:` `Ctrl-w` など）。プラグインの作者は、それを避けてキーを選ぶ。evil-collection が Emacs のパッケージごとに vim 用のキーを作り直しているのは、この決まりがなかったため。
- キーを持たないプラグインのバッファでも、動き、検索、選択、コピーは効く。書き換えるキーは、コアが断って「read-only」と知らせる。
- 利用者が `[settings.keys.*]` で決めたキーは、バッファのキーより先に効く。
- ほかの案を採らない理由:
  - バッファのキーをリーダーの下にだけ置く案は、ぶつからないが、magit や dired の良さである 1 打の操作にならない。
  - 決定（Enter）と閉じる（q）のような意味だけをベースが送る案は、プラグインごとの操作（stage、削除の印）を持てない。
  - modal なベースでもバッファのキーを全部先にする案は、`j` `k` や `/` がプラグインごとに変わり、どのバッファでも覚えたキーで動ける、というバッファにする利点が消える。

## 最初に使うもの

仕組みが足りるかを確かめる役として、標準プラグインの 2 か所をバッファにする。

1. **lsp の診断の一覧**（`lsp.diagnostics`）。開いているファイルの診断を `*diagnostics*` に並べ、Enter でその位置へ飛ぶ（一覧を開いたビューで）。`q` で閉じる。診断が変わるたびに、違うところだけ書き直す（カーソルの行が動かないように）。
2. **vim の `:reg` と Emacs の `C-h k`**。メッセージの 1 行に詰めていたのを、`*registers*` と `*Help*` に書く。`q` で閉じる。
   - Emacs は、ヘルプのウィンドウにフォーカスを移す（`help-window-select` を有効にしたときと同じ）。本物の既定では元のウィンドウに残るが、nib にはほかのウィンドウをスクロールする `C-M-v` がなく、`q` で閉じられるほうを採る。
   - Emacs の `q`（`quit-window`）はウィンドウを閉じ、`*Help*` はバッファの一覧に残る（本物と同じ）。vim の `q` はビューとバッファを閉じる。

- どちらも、一覧を出すときは、フォーカスのあるビューがその一覧でなければ下に分割して出す。ほかのビューにすでに出ていても分かれる（プラグインからはフォーカスのあるビューしか見えないため。ビューの一覧を読む API は、要るものが増えてから考える）。

## API と版

- 足すもの: `buffer.create`、`buffer.name`、`buffer.apply`、`buffer.set-editable`、`buffer.set-keys`、`buffer.keys`、失敗の種類 `read-only`。
- `error` に場合を足し、`buffer-closed` に名前を足すので、0.x の決まりで `nib:plugin@0.7.0`。nib は 0.11.0。

## 入れないもの

- 行ごとに見えない値を持たせる仕組み（テキストプロパティ）。持ち主が行の番号で対応を持てば足りる。
- バッファを開く場所の指定（Emacs の display-buffer のように、下に小さく開くなど）。今は `view.split` と `view.show` で足りる。
- 中身を少しずつ作るための専用の API（遅延の読み込みなど）。
