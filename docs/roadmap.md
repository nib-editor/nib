# ロードマップ

> ステータス: 合意済み（2026-09-25）

各段階は、終えた時点で CI が通り、動くものを確かめられる状態にする。性能は段階ごとに [bench/latency.py](../bench/latency.py) で測り、[architecture.md](architecture.md) の目標と比べる。結果は [benchmarks.md](benchmarks.md) に残す。

## M1 まで

M1 のゴールは、Helix 風キーマップのプラグインだけで、nib 自身のソースコードを編集してコミットできること（[vision.md](vision.md)）。

- バッファ（ropey）、改行コードの判定と復元

確かめ方: 単体テスト。

### M0.2 画面に表示する

### M0.3 プラグインホスト

> 完了（2026-09-25）。プラグインを経由した 1 打鍵の処理は 2.8 µs（release、test-insert プラグイン、Apple M1 Pro）。bench で測ると、test-insert を読み込んだ状態で起動 15.5 ms（コンパイル結果のキャッシュあり）、打鍵は中央値 0.97 ms / p99 1.68 ms（3,455 行の Rust ファイル、ハイライトなし）。
>
> 計画から変えた点:
> - WIT は M1 の全範囲ではなく、実装した範囲（バッファ、ビュー、入力スタック）だけを置いた。コマンド、UI、イベント、縦移動は M0.4 で足す。
> - WIT の検証は wasm-tools ではなく、コアと SDK のビルド（`bindgen!` / `generate!`）で行う。WIT が不正ならビルドが通らない。
> - 実行ファイルへの埋め込みは、埋め込む標準プラグインができる M0.4 に回した。M0.3 では `nib --plugin DIR` でディスクから読み込む。

- `api/` に M1 の範囲の WIT を置き、wasm-tools で検証する
- wasmtime でのプラグインの読み込み（`plugin.toml` と `plugin.wasm`）、`init` の呼び出し
- 時間とメモリの上限、止まったプラグインの片付けと再起動
- コンパイル結果のキャッシュ
- Rust SDK（`sdk/rust`）の最小版
- `cargo xtask` で、プラグインのビルドと実行ファイルへの埋め込み

確かめ方: テスト用の小さなプラグインで、キーを受け取って文字を挿入できること。無限ループするプラグインが止められ、エディタが動き続けること。

### M0.4 helix プラグインの骨格

> 完了（2026-09-25）。helix を埋め込んだ `nib` で、3,455 行の Rust ファイルに対して起動 9.9 ms（コンパイル結果のキャッシュあり）、打鍵は中央値 0.73 ms / p99 2.44 ms（ハイライトなし、Apple M1 Pro）。
>
> 計画から変えた点:
> - コマンドは、コアのコマンド（`buffer.save`、`buffer.open`、`editor.quit`）を呼ぶ `commands.call` だけにした。プラグインがコマンドを登録する `commands.register` とイベントは、使うプラグインが出てくるまで後に回す。
> - コマンドラインは、入力スタックに層を積まず、helix プラグインの内部で扱う（[keymap.md](keymap.md)）。
> - スクロール（`Ctrl-d` など）の API は M1 に回した。

- ノーマルモードと挿入モード
- `h` `j` `k` `l`、`i` `a` `o`、`Esc`、`d`、`u` `U`
- コマンドラインの `:w` と `:q`
- カーソルの形とステータスラインのモード表示
- config.toml の読み込み（`[core]` と `[plugins.<name>]`）と、プラグインからコアの設定を読む API
- コアメニューのプラグイン一覧（選んで再起動、無効と有効の切り替え、ディスクからの読み直し）
- 標準プラグインの実行ファイルへの埋め込み

確かめ方: nib で簡単な編集をして保存できること。キー入力の遅延を bench で測る。

### M1 完成

> 実装は完了（2026-09-25）。3,455 行の Rust ファイル（ハイライトなし、Apple M1 Pro）で、起動 13.1 ms、打鍵は中央値 0.87 ms / p99 3.90 ms、半画面スクロールは中央値 1.14 ms / p99 5.72 ms。待機中の CPU 使用は 1 コアの 0.008%（epoch はプラグインの呼び出し中だけ進める）。確かめ方の「nib のソースを nib で編集してコミットする」は、作者が普段の作業で試す。
>
> 計画から変えた点:
> - `f` / `t` は、Helix と違い、カーソルのある行の中だけを探す。
> - `mm` / `mi` / `ma` の括弧は、構文木を使わずテキストだけで対応を取る。文字列やコメントの中の括弧も数える（M2 で構文木を使う）。
> - キーの割り当て変更は、まだない（M4 に回す）。

- [keymap.md](keymap.md) の「M1 で実装するキー」をすべて実装する
- 複数のバッファ（`:o`、`gn` / `gp`）
- スクロールの API（`Ctrl-d` など）と横スクロール（長い行でもカーソルが見えるようにする）
- ステータスラインで、長いパスでも変更の印（`[+]`）が見えるようにする
- 待機中の epoch の定期起動（10 ms ごと）が電池に与える影響を測る。目立つなら、プラグインの呼び出し中だけ刻むようにする
- 性能目標のうち、打鍵・スクロール・起動を満たす（構文ハイライトは M2 なので、ハイライトなしで測る）

確かめ方: nib のソースを nib で編集してコミットする。

### M2.2 構文木の API

### M2.3 装飾とポップアップ

> 完了（2026-09-25）。対応する括弧の強調は打鍵のたびに構文木を引くが、3,455 行の Rust ファイルで打鍵の遅延に差は見られなかった（強調ありで中央値 2.41 ms / p99 5.26 ms、なしで 2.40 ms / 6.11 ms）。

- バッファの範囲にスタイルを付ける装飾。位置は編集に合わせてコアが動かす
- 位置か右下の角に結びつけるポップアップ
- helix プラグインの、対応する括弧の強調とキーの候補（[keymap.md](keymap.md) の「M2.3 で足す表示」）

行内・行末の文字列と行頭の記号は、LSP と一緒に M3 で作る。

確かめ方: nib のソースで、括弧の上にカーソルを置いたときの強調と、`g` や `m` を押したときの候補を見る。

### M2.4 言語を増やす

> 完了（2026-09-25）。8 言語で `nib` の実行ファイルは 2.7 MB 増えた（文法の分だけ。埋め込みの表を `const` から `static` にして、使う場所ごとに複製されていたのを直した）。起動時は言語を登録するだけで、文法は初めて使うときに読む。

- データだけの言語プラグインを足す: TOML、Markdown、Python、JSON、Go、Bash、YAML
  - 文法とハイライトのクエリは各言語の公式のもの（tree-sitter / tree-sitter-grammars）をそのまま使い、`textobjects` は nib で書く
  - Markdown はブロックの文法だけにする。行内の強調やコードブロックの中の色分けには、ある構文木の中に別の言語の構文木を入れる仕組み（injection）が要るので、あとに回す
- 標準プラグインとして `nib` に埋め込む
- 全部の言語のクエリがコンパイルでき、`maf` などで誤りが出ないことを確かめるテスト

確かめ方: nib のリポジトリの各種ファイル（`Cargo.toml`、`docs/*.md`、`bench/latency.py`、`.github/workflows/*.yml`）を開いて色が付くことを見る。

### M2.5 injection

> 完了（2026-09-26）。3,455 行の Rust ファイル（ドキュメントコメント 592 行）と 6,969 行の Markdown ファイル（ratatui 0.29.0 の `CHANGELOG.md`。コードブロック約 360、行内のコード約 1,000）で測った。数値は [benchmarks.md](benchmarks.md)。Markdown の打鍵は、同じ時に測った injection なしより中央値で約 0.7 ms 遅い（プロセスの中だけで測ると 0.27 → 0.49 ms）。
>
> 計画から変えた点:
> - injection のクエリは、打鍵のたびに構文木の全体へ掛けると 3 ms かかった。前回の結果を覚えておき、構文木が変わった範囲と編集した範囲にだけ掛け直す。組み立て直す層も、変わったものだけにする。
> - 層（injection ごとの構文木）は、画面の近くのものだけを解析して持つ。Markdown は段落ごとに行内の層があり、6,969 行のファイルでは 1,709 層になる。全部を解析すると 240 ms、全部に編集を伝えると 1 打鍵に 1 ms かかった。
> - 最初の解析では injection を後回しにし、元の言語の色を先に出す。

- 言語プラグインの `injections` クエリ（[architecture.md](architecture.md) の「構文木」）。コアが、その範囲だけを別の言語で解析する層を持ち、ハイライトを重ねる
- Markdown のコードブロック（情報文字列の言語名か拡張子で言語を選ぶ）と front matter（YAML / TOML）
- Markdown の行内の要素（強調、コード、リンク）。行内の文法（`markdown_inline`）を Markdown のプラグインに足した
- Rust のドキュメントコメントを Markdown として（ファイルの全部のドキュメントコメントで 1 つの文書にする）

確かめ方: nib のリポジトリの `docs/*.md` のコードブロックと行内のコード、`core/src/*.rs` のドキュメントコメントに色が付くことを見る。

### M2.6 解析を裏のスレッドへ

> 完了（2026-09-27）。同じ時に、裏で解析しない nib と比べた打鍵（中央値 / p99）は、3,455 行の Rust ファイルで 2.41 / 5.15 ms → 1.61 / 3.38 ms、6,969 行の Markdown ファイルで 2.53 / 6.10 ms → 1.74 / 4.39 ms。スクロールは変わらない。残りの大半は、描画でハイライトのクエリを掛ける分（プロセスの中で 0.17 ms）。解析のあいだに打った編集の当て直しは、同期で解析した画面と 1 マスずつ比べるテストで確かめる。

設計は [architecture.md](architecture.md) の「解析のスレッド」。

- undo と redo を、構文木を捨てずに編集として伝える
- コアの `editor.syntax_updated` イベントと、helix の括弧の強調をそれで更新すること
- 解析の専用スレッドと、tui での有効化

確かめ方: 3,455 行の Rust ファイルと 6,969 行の Markdown ファイルで、打鍵の遅延（最初の画面まで）が、構文ハイライトのないテキストファイルに近づくこと。解析のあいだに打った編集が、結果に正しく当て直されること。

### M2.7 ハイライトの使い回しと、injection の層の解析をスレッドへ

> 完了（2026-09-27）。打鍵（中央値）は、3,455 行の Rust ファイルで 1.61 → 0.61 ms、6,969 行の Markdown ファイルで 1.74 → 0.71 ms と、構文ハイライトのないテキストファイル（約 0.6 ms）に並んだ。ドキュメントコメントの中で打ったときのメインスレッドの仕事は、最大 3.2 ms から 0.22 ms になった。
>
> 確かめ方: 使い回した色は、編集の直後（古い構文木で描くフレーム）と解析のあとの両方で、全体を塗り直した色と比べる。層の解析のあいだに打った編集は、同期で解析したエディタの画面と比べる。どちらのテストも、壊した実装（編集した行を塗り直さない、当て直した編集を層の中の injection に伝えない）で落ちることを確かめた。

設計は [architecture.md](architecture.md) の「構文木」と「解析のスレッド」。

- 前のフレームのハイライトを使い回し、編集した行だけ塗り直す
- injection の層の解析を、解析のスレッドに頼む

確かめ方: 打鍵の遅延（3,455 行の Rust ファイル、6,969 行の Markdown ファイル）と、ドキュメントコメントの中で打ったときのメインスレッドの仕事の時間。使い回した色が、全体を塗り直した色と同じであること。

エディタとして普段使いするのに足りないもの（ほかのプラグインとの連携、外部プロセス、ファイル選択、LSP）をそろえる。

### M3.1 コマンドの登録、イベント、タイマー

> 完了（2026-09-26）。プラグインは `run-command` と `on-event` を実装する必要があるので、既存のプラグインはそのままでは読み込めない（SDK 0.2.0）。

- `commands.register` と guest の `run-command`。プラグインのコマンドを同期的に呼べるようにする（呼び出し中のプラグインへの貸し出しを、呼び出し先に又貸しする）
- guest の `on-event` と、マニフェストの `events` による購読。`buffer-opened`、`buffer-saved`、`buffer-changed`、custom イベント（`events.emit`）
- `timers.set` / `timers.cancel` と、タイマーを待つメインループ
- `editor.buffers()`
- helix プラグインが `helix.mode_changed` を出す

確かめ方: テスト用のプラグインで、コマンドの呼び合い、再入のエラー、イベントの順番、タイマーを確かめる。

### M3.2 外部プロセスと権限

> 完了（2026-09-26）。入力のスレッドに移しても、打鍵の遅延は変わらなかった（中央値 1.29 ms / p99 6.16 ms）。

- マニフェストの `capabilities` と、宣言していない権限を与えないこと（`process`、`fs-read`、`fs-write`、`network`）。Ctrl-g のメニューに権限を出す
- `process.spawn` と、出力・終了のイベント。入力の読み取りを裏のスレッドに移し、キー入力と外部プロセスの出力を 1 つのキューで待つ

確かめ方: テスト用のプラグインで、起動、標準入力への書き込み、出力と終了のイベント、権限がないときのエラーを確かめる（Linux / macOS / Windows の CI で）。

### M3.3 ファイル選択

> 完了（2026-09-26）。コアの非同期ファイル列挙は、M4.4 で足した。

- あいまい検索で選ぶファイル選択のプラグイン（`picker`）と、helix の `Space f`
  - ファイルの一覧は、まず `git ls-files` で得て、git のリポジトリでなければ `rg --files` で得る。どちらも `.gitignore` を守り、外部プロセスの API で待たずに受け取れる
  - あいまい検索は自前で書く（候補が数万件でも、打鍵ごとに数 ms で終わる程度の簡単なもの）
- コアの非同期ファイル列挙（`.gitignore` を守る）は、依存に `ignore` クレートを足すことになるので、足してよいか決めてから作る。作ったら `picker` の一覧の取り方をそちらに替える

確かめ方: nib のリポジトリで `Space f` から `Cargo.toml` などを開く。

### M3.4 LSP

## 1.0.0

1.0.0 で最初のリリースを出す（[distribution.md](distribution.md)）。1.0.0 は「このあと 1.x のあいだは互換を保つ」約束の区切りなので、約束するものを先に固める。次の 4 つがそろったら 1.0.0 にする（2026-09-28 に決めた）。

- **プラグイン API を固める**: WIT を見直し、足りないもの（貼り付けや選択の変化のイベントなど。今は「必要になったら足す」にしてある）と、名前や形の揃わないところ（コアが custom イベントの形で出している `editor.*` を正式な種類にするかなど）を直して、`nib:plugin@1.0.0` にする。1.x のあいだは、足すことはあっても、変えたり消したりしない。SDK も 1.0.0 にする。（0.10.0 で、`nib:plugin@0.6.0` として作り直した: コアの操作とイベントを型に、interface の分け直し、ベースで困ったものを足した。1.0 で固めるときの決まりも含めて [api-0.6.md](api-0.6.md)）
- **設定の形を固める**: `config.toml`、`plugins/<name>.toml`、helix のキーの書き方を見直す。1.x のあいだは、今の書き方で書いた設定が読めなくなる変更をしない。
- **自分で普段の編集に使える**: 普段のコードや文章の編集に nib を使い、困ったことを直す。見つけたことは、この節の下に足していく。
- **利用者向けの文書（英語）**: キー、設定、言語、LSP、プラグインの入れ方を、使う人向けに英語で書く。今あるのは README と、作者向けの `sdk/README.md` と、設計の記録（日本語の docs）だけ。

配布の仕組み（リリースのワークフロー、Homebrew の tap、Scoop の bucket、crates.io の準備）は用意してあり、1.0.0 のタグを打てば動く。
