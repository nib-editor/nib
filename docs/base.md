# ベースプラグイン

> ステータス: 合意済み（2026-09-27）

helix 以外の操作感（vim、Emacs、nano）を足すにあたり、「エディタの操作感を丸ごと持つプラグイン」をベースと呼び、その作り方と、ベース同士で何を共通にするか、コアに何を足すかを決める。[keymap.md](keymap.md) の Helix 風キーマップは、最初のベースになる。

## ベースとは

- ベースは、1 つのエディタの操作感を丸ごと持つプラグイン。キーの割り当て、モード、編集の作法、コマンド入力（`:` やミニバッファ）の作法まで含む。
- 標準のベースは `helix`、`nano`、`vim`、`emacs` を予定する。ユーザーが自分のベースを作れるようにもする。そのため、ベースに要るものは公開の API だけで作れるようにする。
- **同時に動くベースは 1 つだけ。** 複数が動くと、どちらもいちばん下の入力の層としてキーを取り合う。

エディタごとに分けるのは、同じ名前の機能でも作法が違うため。1 つの共通のベースにまとめると、どれかに無理が出る。

| | helix | vim | Emacs | nano |
|---|---|---|---|---|
| 単語移動 | 単語を選択する | カーソルを動かす | 単語の終わりへ | カーソルを動かす |
| コピーの置き場 | レジスタ | 名前付きレジスタ | キルリング | カットバッファ |
| 繰り返し | マクロ | `.` とマクロ | `C-x z` とマクロ | なし |
| コマンドを名前で呼ぶ | `:` | `:` | `M-x` | なし（下の「コマンドを名前で呼ぶ」） |
| 取り消し | Esc | Esc | `C-g` | `^C` |

## どこまで再現するか

- 目標は「指が覚えている操作が期待どおり動く」こと。元のエディタのすべては再現しない。違いは各ベースの文書に書く。
- 本物と比べるテストで、どこまで同じかを測る。同じキー列を `nvim --headless` や `emacs --batch` と nib に流し、テキストとカーソルの位置を比べる。
- vim と Emacs のコードは読まない。文書と実際の動作から作る。Emacs は GPL-3 で、写すと nib のライセンスを縛るため。比べるテストは動作を比べるだけなので構わない。

## 選び方

`config.toml` の `[core]` で 1 つ選ぶ。既定は `helix`。

```toml
[core]
base = "vim"
```

- ベースかどうかは、プラグインの `plugin.toml` に書く（`base = true`）。コアは、`[core] base` で選ばれたもの以外のベースを読み込まない。使わないベースのぶん、起動の時間とメモリが増えない。
- 選ばれたベースが見つからない、または読み込みに失敗したら、`helix` で起動し、そのことをメッセージで知らせる。ベースがないとキーで何もできないため。
- コアのメニューから、再起動なしでベースを切り替えられる。切り替えると、前のベースの状態（レジスタなど）は消える。
- 最初の起動で、どのベースを使うかを聞く。ほかのエディタから来た人が、すぐ慣れた操作で使い始められるように。helix のほかにベースができてから入れる。

## メニューのキーと、止めるキー

いまは Ctrl-g が「コアのメニューを開く」と「実行中のプラグインを止める」を兼ねている。Emacs では `C-g` がいちばんよく使う取り消しのキーなので、2 つを分ける。

- **止めるキー**は `C-g` のまま。プラグインが動いている間だけ、コアが受け取る。Emacs の `C-g` と意味が同じ。
- **メニューのキー**は、ベースが `plugin.toml` に書く（`menu-key`）。コアはベースのコードを動かさずに読めるので、ベースが壊れていてもメニューを開ける。
  - helix と vim は `C-g`、nano は `^G`（nano ではもともとヘルプ）、Emacs は `F10`（Emacs でメニューバーを開くキー）。
  - ユーザーは今までどおり `[core] menu-key` で上書きできる。
- メニューはコマンド（`core.menu`）でも開ける。ベースが `:menu` や `M-x` から呼べる。

## キーの上書き

各ベースの設定（`plugins/<ベース>.toml`）の `[settings.keys.<モード>]` に書く。いまの helix と同じ形。

```toml
# plugins/vim.toml
[settings.keys.normal]
"C-s" = "buffer.save"
g = { d = "lsp.definition" }   # 表は前置きキーになる

# plugins/emacs.toml（モードがないので global）
[settings.keys.global]
"C-x" = { "C-r" = "picker.recent" }
```

- `config.toml` には書かない。ベースを変えるたびにキーの設定を書き換えずに済み、ベースを行き来してもそれぞれの上書きが残る。
- モードの名前はベースが決める（vim は `normal` / `insert` / `visual`、Emacs と nano は `global`）。
- キーの書き方（`C-x`、`M-f`、`S-tab`、前置きキーの表）は全ベースで同じにする。
- 右辺は、そのベースのアクションの名前か、コマンドの名前（`buffer.save`、`lsp.definition`）。

## 他のプラグインのキー: リーダー

ベースでないプラグインのコマンドを、どのキーで呼ぶかを決める。

- 各ベースは、プラグインのためのキーの置き場（リーダー）を 1 つ持つ。helix は `space`、vim は `<leader>`（既定は `space`）、Emacs は `C-c`、nano は `M-`（未使用のもの）。`plugin.toml` に書く（`leader`）。
- プラグインは `plugin.toml` に、リーダーからの相対でキーを書く。どのベースでも、そのベースの作法の場所に入る。自作のベースも、リーダーを持てばそのまま対応する。

  ```toml
  [keys]
  w = "wordcount.show"          # helix なら space w、Emacs なら C-c w
  "c d" = "lsp.definition"      # グループ c の中
  ```

- リーダーの下のグループ（`f` ファイル、`b` バッファ、`s` 検索、`c` コード、`g` git）は、推奨の慣習とする。必須にはしない。
- キーがぶつかったら、ユーザーの設定が勝ち、次に先に入れたプラグインが勝つ。負けたものは、次のキーの候補の表示と `nib plugin list` で分かるようにする。
- 定義へ飛ぶ（vim の `gd`、Emacs の `M-.`）のように、元のエディタに決まったキーがある機能は、ベースが直接割り当てる。
- ほかの案を採らない理由:
  - プラグインがベースごとにキーを書く（`[keys.vim]` など）と、自作のベースに対応できない。Emacs のパッケージを vim 風に割り当て直すだけの大きな別プロジェクト（evil-collection）があるのは、この形の行き着く先。
  - キーを持たずにユーザーが全部割り当てるのは、入れるたびに設定が要る。

## コマンドを名前で呼ぶ

キー、リーダー、コマンド入力のどれからでも、同じコマンドの名前を呼ぶ。

- helix と vim は `:` から、Emacs は `M-x` から、登録されたすべてのコマンドを名前で呼べる（`:lsp.definition`、`M-x lsp.definition`）。打っている途中で、コマンドの一覧と説明から補完する。
- `:w` や `save-buffer` のような元のエディタの名前は、ベースが別名として持つ。
- nano には名前でコマンドを呼ぶ仕組みがない。`^T`（nano 5 以降の Execute）で、コマンドの一覧（パレット）を開く。名前を覚えて打つより、説明を見ながら絞り込んで選ぶ方が nano の使い方になじむ。
- パレットは picker プラグインの機能（`picker.commands`）にし、どのベースからも呼べるようにする（helix は `space ?`）。
- コマンドの一覧と説明をプラグインが取れる API と、`:config indent` のような 1 語の引数を JSON の引数にどう渡すかを決める（1.0.0 の前に）。

## プラグインの画面の操作: 仕組みはコア、作法はベース

picker や補完の一覧のようなプラグインの画面を、ベースの作法で操作できるようにする。いまの picker は `C-n` / `C-p` / Backspace / Esc を自分で決めていて、どのエディタの作法にも合っていない。

- **画面は、キーではなく操作の意味を受け取る。** 「次」「前」「決定」「閉じる」「補完」「スクロール」など。どのキーをどの操作にするかはベースが決める（Emacs なら `C-n` と `C-g`、vim なら `C-n` と Esc）。
- **文字を打つ欄は、仕組みをコアが、作法をベースが持つ。** コアが持つのは、文字列、カーソル、描画、誰が開いたか。`C-w` で単語を消す、`C-a` で先頭へ、のようなキーの解釈はベースが持つ。ベース自身の `:` や `M-x` も、picker の検索欄も、同じ仕組みで動く。
- **ベースが対応していない操作は、コアの既定のキーで動く**（上下、Enter、Esc、Backspace、文字）。作りかけの自作のベースでも、picker が使える。

## コアに足すもの

- 上の、文字を打つ欄と、画面の操作の意味。
- **編集に合わせて動く位置の印。** vim のマーク（`ma`）とジャンプリスト、Emacs のマークとマークリングは、どれも編集されても正しい場所を指し続ける位置。ベースが自分で持つと、LSP の整形のような他のプラグインの編集でずれる。すでにある、編集に合わせて動く装飾と注釈の仕組みを使う。
- コマンドの一覧と説明を取る API。
- `plugin.toml` の `base` / `menu-key` / `leader` / `[keys]`、`[core] base`、ベースの切り替え。

選択は今の形（範囲の組）のままで足りる。vim は幅 1 の範囲、Emacs はカーソル位置の範囲とマーク（位置の印）、vim の矩形選択と Emacs の矩形は複数の範囲で表す。undo はコアのものを使う。Emacs の「undo を undo する」作りは再現せず、Emacs 28 の `undo-redo` と同じ動きにする。

## 共通にするもの: 共有ライブラリ

ベース同士の共通部分は、ビルドのときに各ベースに取り込む Rust のライブラリに置く。実行時のプラグインにはしない。

- 同時に動くベースは 1 つなので、実行時に共有するものがない。
- プラグインをまたぐ呼び出しが増えず、1 キーの処理が今と同じ速さのまま。
- プラグイン API の外なので、1.0.0 のあとでも作り替えられる。

置き場所は、はじめは標準プラグインのワークスペースの中（`plugins/base-kit/`、プラグインではないライブラリ）にする。自作のベースの作者が使いたくなったら、SDK として出すかを考える。Go で書くベースは使えない。

いまの helix（約 2,700 行）の振り分けの目安:

| 中身 | 行数 | 置き場所 |
|------|------|----------|
| 文字と行の読み出し、単語の境界、文字探し（`f`）、括弧の対応 | 約 400 | ライブラリ |
| tree-sitter のテキストオブジェクト、選択の広げ縮め | 約 170 | ライブラリ |
| キーの書き方の読み書き、`[settings.keys.*]` の上書き | 約 250 | ライブラリ（アクションの一覧はベース） |
| 次のキーの候補の表示 | 約 50 | ライブラリ（中身はベースが渡す） |
| コマンド入力（`:`、`M-x`）: 名前での呼び出し、補完の候補、別名、引数の渡し方。`:w` `:q` `:config` などの別名の表 | 約 100 | ライブラリ（別名の表はベースごとに足せる） |
| リーダー: プラグインの `[keys]` をリーダーの下に組み込み、ぶつかりを解く | 新規 | ライブラリ |
| 編集の適用、貼り付け、インデントの増減、行の連結、検索の折り返し、置き換え | 約 550 | ライブラリ |
| モード、キーの割り当て、押しかけのキー、選択が先に来る動き方、レジスタ、繰り返し、入力欄のキーの解釈 | 約 1,150 | helix |

コマンド入力とリーダーをライブラリに置くのは、中身（名前を引く、補完の候補を出す、プラグインのキーを組み込む）がどのベースでも同じで、違うのはどのキーで開くかと入力欄のキーの解釈だけだから。自作のベースも、これを使えば `:` や `M-x` とリーダーをすぐ持てる。

線の引き方: ライブラリは「位置を求める」「編集を組み立てる」まで。「その位置でカーソルを動かすか選ぶか」「消したものをどこに置くか」はベース。レジスタとキルリングのように作りの違うものは、無理に共通にしない。

## 進め方

1. helix からライブラリを切り出す。helix の動作は変えず、今のテストで確かめる。（済み）
2. `plugin.toml` の `base` / `menu-key` と `[core] base`、メニューからの切り替え。止めるキーとメニューのキーを分ける。（済み。`[core] base` を変えて設定を読み直しても切り替わる。メニューでの切り替えはその場限りで、残すには `[core] base` に書く）
3. コマンドの一覧の API、`:` から名前で呼ぶこと、パレット（`picker.commands`）。
4. 文字を打つ欄と画面の操作の意味をコアに足し、helix の `:` と picker を載せ替える。
5. リーダーと `plugin.toml` の `[keys]`。
6. nano を作る。ライブラリとコアの仕組みで足りるかを確かめる役。最初の起動で聞くのもここで入れる。
7. 位置の印をコアに足し、vim と Emacs を作る。本物と比べるテストも作る。
8. 標準で同梱するかは、各ベースの大きさを測ってから決める（一つで数百 KB の見込み）。

2〜5 と 7 の位置の印は API を変えるので、1.0.0 で API を固める前に済ませる。
